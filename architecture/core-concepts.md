# Core Concepts: Fixtures, Channels, Beams, Kinds

This document explains the foundational data models that represent physical lights within Pixelmapper. The **canonical model** is fixtures → channels → beams. Everything the engine, canvas, 3D view and connectors consume is expressed in it; fixture kinds from extensions *compile into* it (ADR D15).

## FixtureGroup

A `FixtureGroup` is a logical container that can hold `Fixture`s or other `FixtureGroup`s, forming a hierarchy (similar to Figma layers).

- **`id`** — Unique identifier.
- **`name`** — Display name (e.g., "Front Wash").
- **`children: SceneNode[]`** — Nested nodes within this group.
- **`parent: FixtureGroup | null`** — Reference to the parent group, if any.
- **`getAllFixtures()`** — Recursively extracts all descendant fixtures.

The primary node array `sceneNodes` is a `shallowRef` in Pinia. This deliberately prevents Vue from building deep reactive proxy graphs over the entire scene. Adding or removing nodes replaces the array reference or calls `triggerRef(sceneNodes)`.

**Rotating groups** (`app/utils/engine/group-rotation.ts`): when a group is selected, rotating it turns the group as one unit. Its member fixtures spin by the delta and orbit the center of the members' bounding box. A fixture selected on its own, including a group member selected by drilling in, spins in place. This applies to the 2D rotation handles, the inspector's R field and the 3D gizmo's yaw (tilt and roll stay per fixture). `RotateFixture` snapshots carry optional `x`/`y` for orbiting members, so undo/redo and the sync rebase adapter restore their positions too.

## Fixture

A `Fixture` represents a physical light device. Fixtures are stored inside a `shallowRef` and act as plain JavaScript objects — not Vue reactive proxies. This Data-Oriented Design (DoD) choice prevents Vue from tracking thousands of nested properties at 60 fps.

- **`id: string | number`** — Identifier (`ofl-N` for added fixtures). The fixture's position in the flat list is its `group_index` in the binary layout packet.
- **`name`** — Display name.
- **`startAddress: number`** — 1-based DMX universe address for this fixture's footprint.
- **`channels: Channel[]`** — The DMX channels this fixture exposes.
- **`fixturePosition: { x, y }`** — World-space position, normalized 0–1.
- **`fixtureSize: { x, y }`** — Size multiplier for beam offset calculations.
- **`rotation: number`** — Rotation in degrees, applied to beam local offsets.
- **`beams: Beam[]`** — One or more output points of light (see below).
- **`kind?: { id, version, config, compiled }`** — Set for fixtures generated by a fixture kind (see below).
- **`extensionData?`** — Namespaced extension data `extensionData[extensionId][key]` (JSON, written via `SetExtensionData`).
- **`resolveColor(dmxBuffer): string`** — Computes the fixture's current visual color from its channels, reading values directly from the DMX buffer.

## Channel

Each channel is structural metadata — an offset pointer into the DMX universe. It does not store live `value` state; that lives in the engine's `dmx_buffer` and `base_buffer` typed arrays.

- **`type: ChannelType`** — e.g. `RED`, `GREEN`, `BLUE`, `DIMMER`, `PAN`, `TILT`, `FOG`, etc.
- **`addressOffset: number`** — 0-based offset within the fixture's DMX footprint.
- **`chaserConfig: ChaserConfig`** — Defines step values, playback state, and timing.
- **`beamId`** — Optional reference to a `Beam` within the fixture (for multi-beam fixtures).
- **`role: ChannelRole`** — How this channel participates in color rendering:
  - `COLOR` — Contributes additively to the fixture's visual color. Requires `colorValue` (hex).
  - `DIMMER` — Scales all COLOR channels (0 = off, 255 = full brightness).
  - `NONE` — No visual contribution (PAN, TILT, FOG, etc.).

## Beam

A `Beam` lives inside a `Fixture` and represents a single output point of light.

- **`id`** — Identifier within the fixture. For matrix/custom SVG fixtures this equals the OFL pixel key (e.g. `head-1`, `head-2`, …).
- **`localX`, `localY`** — Offset relative to the fixture's world position, in local fixture space (range roughly −0.5 … +0.5).
- **`offsetPx`** *(kind beams)* — Center in world pixels relative to the fixture origin; replaces the normalized offset.
- **`emitters`, `emitterRadius`** *(kind beams)* — Physical emitters sharing the beam's color (e.g. the LEDs of one strip pixel group), drawn as dots in 2D and points in 3D.

### Beam position sources

| Fixture type | localX / localY source |
|---|---|
| Standard matrix | Uniform grid: `(x / (n−1) − 0.5) × spreadFactor` |
| Custom SVG (with `headPositions`) | SVG element centroid: `(pos.x − 0.5) × 0.95` |
| Custom SVG (legacy, no `headPositions`) | Uniform grid fallback |

For custom SVG fixtures the true element centroid is computed once at save-time (see `computeHeadElementCentroids` in `app/utils/engine/svg-element-positions.ts`) and stored in `pixelmapper.customSvg.headPositions`. The bbox center is mapped through the element→root CTM, so heads placed via `transform` (typical for Affinity/Illustrator/Figma exports) get distinct positions. `createFixtureFromOfl` recomputes the centroids from the SVG whenever a DOM is available and only falls back to the stored ones otherwise. This ensures modifier fanning spreads phase correctly even for non-linear arrangements (circles, fans, etc.).

### Multi-head fixtures in 3D

`buildSceneModel` (`app/components/three/scene/fixture-adapter.ts`) places every beam at its own position on the fixture footprint. Multi-head fixtures additionally get:

- **Emitting face** (`SegmentModel`, rendered by `pixel-segments.ts`): one quad per head on the body box's top face, filled with that head's live color every frame, so pixel effects are readable along a bar.
- **Per-head beam cones**: when the fixture has a lens or pan/tilt, each head gets its own cone at its position and color (no moving-head box). Single-head fixtures keep one cone with a head box at the fixture origin.

### Moving heads in 3D

Single-head fixtures with a positional PAN or TILT channel get a procedural model (`moving-head-geometry.ts` for proportions, `beam-cones.ts` for the rig): the base is the fixture's selection body box, a pan bearing and U-yoke rotate with pan, and the head barrel tilts about the yoke axis with a lens that glows in the beam color. The cone starts at the lens.

- **Frame**: origin = center of the base's bottom face (mounting plane). The neutral pose (pan/tilt at their DMX midpoint) points the beam along local +Y — up for a floor-standing fixture. Hanging fixtures use the fixture's Tilt = 180°.
- **Size**: OFL `physical.dimensions` [w, h, d] mm, persisted as `Fixture.dimensionsMm`; without them the median OFL moving head (296×389×243 mm) scaled to the footprint.
- **Motion range**: `Fixture.motionRange` (`app/utils/engine/core/motion-range.ts`) stores the OFL `angleStart`/`angleEnd` of the positional Pan/Tilt capability at creation (channel `oflCapabilities` are not persisted). Angles are centered: DMX 0 → −range/2, DMX max → +range/2; inverted ranges keep their direction. Percent angles fall back to 540°/270°; `PanContinuous`/`TiltContinuous`-only channels are speed controls and don't move the pose.
- **Resolution**: coarse PAN/TILT are linked to their fine channel whenever OFL `fineChannelAliases` is set (`dmxValueResolution` is optional in OFL and only gives the unit of ranges/defaults), so the 3D pose and the engine's head targets are 16-bit.

When `buildLayoutBin` computes `world_x/world_y` for each channel, it uses `beamWorldPx(fixture, beam)` (`app/utils/kinds/kind-host.ts`): kind beams rotate their `offsetPx` about the fixture origin; classic beams scale the normalized offset by the fixture footprint and rotate it:

```typescript
const a = fixture.rotation * (Math.PI / 180)
const px = beam.localX * fixture.fixtureSize.x * FIXTURE_RADIUS * 2
const py = beam.localY * fixture.fixtureSize.y * FIXTURE_RADIUS * 2
world = origin + (px·cos a − py·sin a, px·sin a + py·cos a)
```

This transform is encoded once into the layout packet, so the engine sees final spatial coordinates.

## Fixture kinds (ADR §5.6)

A **fixture kind** is an extension contribution (`contributes.fixtureKinds`) that turns a JSON config into the canonical model. The core has no kind-specific code; it only knows the generic results.

```ts
defineFixtureKind<Config>({
  id, version, label, icon, description,
  configSchema,                 // ParamSchema → generic add form + selection-panel editor
  defaults(): Config,
  build(config, ctx): { channels, beams, body, handles, bounds },  // pure
  onHandleMove?(config, handleId, pos, ctx): Config,                // pure
  onHandleDelete?(config, handleId, ctx): Config,                   // pure
  migrate?(config, fromVersion): Config,
  library: { category, addForm? },
  requiredWhenUsed?, spansUniverses?,
})
```

- **Coordinates:** everything `build` returns is in world pixels **relative to the fixture origin** (`fixturePosition`). The core applies position and rotation (`kindToWorld` / `worldToKind`), so moving and rotating kind fixtures needs no kind code.
- **State:** `fixture.kind = { id, version, config, compiled }`. `config` is the source of truth; `compiled` caches the last build and is used when the kind's extension is missing. Every load rebuilds from `config` (migrating older `version`s). Rebuilds keep programmed values of channels with the same offset and type.
- **Edits:** all config changes go through the core `SetFixtureKindConfig` command (one undo step; scrubs coalesce). The selection panel renders `configSchema` with `ParamForm`; extensions can call `ctx.commands.setFixtureKindConfig`.
- **Addressing:** new fixtures get consecutive addresses; a fixture that would cross a 512-channel universe boundary starts a new universe unless its kind sets `spansUniverses` (pixel strips fed as one buffer).

### Body primitives

| Primitive | 2D canvas (Rust) | 3D |
|---|---|---|
| `polyline { points, closed?, width, style }` | stroked path | tube (`body-polylines.ts`) |
| `polygon { points, style }` | filled/stroked | flat shape (`body-shapes.ts`) |
| `circle { center, radius, style }` | filled/stroked | flat shape |
| `rect { rect, radius?, style }` | filled/stroked (polygon when rotated) | flat shape |
| `svg { markup, headElementMap, rect }` | — (core SVG fixtures use the custom-SVG path) | textured plane (`svg-planes.ts`) |

`style` colors are CSS colors or theme variables (`var(--primary)`), resolved to RGBA by the host. Beams with `emitters` are drawn as dots in their resolved DMX color. Selection outlines follow the body; precise hit-testing uses the body and emitters.

### Handles and edit mode

`handles: { id, pos, role }[]` with roles `anchor`, `vertex`, `midpoint`, `rotate`. **Anchors** are active whenever the fixture is selected; all other roles only in **edit mode**, entered by clicking an already-selected fixture that has non-anchor handles. Dragging a handle calls `onHandleMove(startConfig, id, pointer)` on every move — always from the drag-start config — and commits one `SetFixtureKindConfig` on release. Delete/Backspace (or right-click) on a focused handle calls `onHandleDelete`.

### Example: `extensions/neopixel-strip`

Config `{ shapeType, chipType, ledCount, ledsPerMeter, groupSize, clockwise, points }`. `build` samples the bezier/line/circle (Catmull-Rom sampling lives in the extension), emits RGB(W) channels per logical pixel, one beam per pixel with every physical LED as an emitter, the capped curve as a `polyline` body, vertex/midpoint handles for bezier shapes and endpoint anchors for lines.

## ChaserConfig

Defines how a DMX channel's value steps over time:

```typescript
interface ChaserConfig {
    stepValues:     number[]    // DMX values (0–255) per step
    stepsCount:     number
    activeEditStep: number      // which step is shown in the UI
    isPlaying:      boolean     // whether the chaser is running
    stepDuration:   SpeedConfig // how long each step lasts
    fadeDuration:   SpeedConfig // crossfade time between steps
}
```

A chaser with `stepsCount=1` and `isPlaying=false` is simply a static value — the common case for faders. The Rust engine handles both cases in the same code path.

## RenderTarget

The engine's internal per-channel view, built from the layout packet:

```rust
pub struct RenderTarget {
    pub dmx_index:       usize,
    pub channel_type_id: u8,
    pub group_index:     usize,   // position of the fixture in the flat list
    pub head_index:      usize,   // beam index (rgb / panTilt heads)
    pub world_x:         f32,
    pub world_y:         f32,
    pub resolution:      u8,
    pub chaser_config:   Option<ChaserConfig>,
    // … fine offsets, range min/max
}
```

`targets` is populated by `sync_layout` and updated by `sync_channels`. Modifiers use `group_index`, `channel_type_id`, `head_index`, `world_x`, `world_y` to build their samples (see [engine.md](engine.md)).
